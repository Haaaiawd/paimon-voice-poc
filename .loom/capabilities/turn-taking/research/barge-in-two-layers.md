# Barge-in 的两层正确性

Source: Picovoice Voice UX guide ch.3

Barge-in 不是边界情况，是人类纠正、跳过、改话题的方式。agent 压过用户的打断把话说完，
传达的是"用户没有控制权"，这种印象洗不掉。

正确的 barge-in 必须两层同时触发：
- 媒体层：播放中检测到入向语音的瞬间，停止/静音出站音频并冲刷播放 buffer。
  这里检测用的还是 VAD，只是跑在 agent 发声期间——所以回声处理重要：agent 不能打断自己
  （本项目第一版用耳机规避）；
- 逻辑层：取消/作废所有在途工作。pending 的 LLM 生成、排队的 TTS 任务、未执行的函数调用
  若在打断后存活，会作为"用户已放弃的问题"的陈旧响应重新浮现——陈旧响应是半成品
  barge-in 的签名式失败。

打断后系统带着完整对话状态回到 listening：用户的打断是新轮次的开始，agent 已产出的部分
响应要以"被打断的轮次"留在对话历史里，而不是抹掉——推理层需要知道用户听到了什么、没听到什么。

生产指标：barge-in latency = 用户打断的第一个音节 → agent 静音。可从事件日志测量，
与用户是否觉得 agent"在听"直接相关。
